# GAMEGAM 战斗规则合同（combat_rules.md）

日期：2026-10-05。状态：**草稿**。承接 `godot_architecture.md` 第 5.5、8 节"实现前必须写清"的规则。

本文是**精确合同**：实现与测试都以此为准。凡是写【建议默认】的，是可调数值/可在原型中改动的默认决定；凡是写"必须"的，是实现硬约束，改动需同步更新本文件。数值（费用、伤害、抽牌数）不在此列，见内容资源。

术语：**命令** = 一次 `submit()` 输入；**结算** = 命令被接受后对工作状态的规则变换；**结算边界** = 效果/触发队列排空的时刻；**权威状态** = 已提交的 `BattleState`。

## 1. 阶段与结算边界（状态机）

```text
SETUP → ROUND_START → PLAYER_INPUT
PLAYER_INPUT ──(PlayCards/Move)──→ RESOLVING → PLAYER_INPUT
PLAYER_INPUT ──(EndTurn)────────→ PLAYER_END → ENEMY_ACT → ROUND_END → ROUND_START
任意结算边界 → VICTORY / DEFEAT
```

硬约束：

- **只有 `PLAYER_INPUT` 接受命令。** 其余阶段 `submit()` 一律拒绝（错误码 `E_PHASE`），不产生任何副作用。
- **命令锁**：`RESOLVING` 期间（表现层在播放事件）`submit()` 必须拒绝（错误码 `E_BUSY`）。命令锁属于 `BattleState`，随存档持久化。UI 门禁只是视觉，**不是**权威。
- **终态**：进入 `VICTORY` / `DEFEAT` 后，除清理外不再产生伤害、位移或触发；后续 `submit()` 拒绝。
- **结算边界判定**：每个结算边界（队列排空）后重新评估胜负（§11）。`VICTORY`/`DEFEAT` 是**终态结算边界**——到达后立即停止生成新的攻击类效果，只完成牌区清理（§4.6）再转入终态。

## 2. 回合内时序

【建议默认】时序如下，改动需记入本表：

| 时刻 | 内容 |
|---|---|
| `ROUND_START` | ① 结算 tick 时机为 ROUND_START 的状态 ② 玩家补手牌至 N（抽牌堆空则洗弃牌堆） ③ **锁定本回合敌人意图**（§5.6 EnemyPlanner） ④ 判胜负 |
| `PLAYER_INPUT` | 接受玩家命令，直到 `EndTurn` |
| `PLAYER_END` | ① 结算 tick 时机为 OWNER_TURN_END 的玩家状态 ② 结算玩家 end-of-turn 触发（遗物等） ③ 【建议默认】弃掉剩余手牌 |
| `ENEMY_ACT` | 按固定玩家→敌人顺序、敌人在其内部按稳定 ID 顺序执行**已锁定意图** |
| `ROUND_END` | ① 全部单位结算 tick 时机为 ROUND_END 的状态 ② 清除本回合临时修正（非持久） ③ 判胜负 |

要点：

- 敌人意图在**玩家行动前**锁定并给 UI 预告；执行前若因玩家行动而失效，按 §5 的降级规则处理，**不重算**整轮意图（除非该敌人被明确重新规划）。
- 玩家与敌人复用同一套效果结算服务；差异只在输入来源（UI vs EnemyPlanner）。

## 3. 命令合同

`BattleSession.submit(command) -> CommandResult`。校验顺序（**必须**按下表，前项失败即返回，不进入后项）：

| 序 | 校验 | 失败错误码 |
|---|---|---|
| 1 | 命令 ID 未见过（去重，§12.3） | `E_DUPLICATE`（幂等：重放同一命令返回首次结果） |
| 2 | 阶段接受输入且命令锁未置位 | `E_PHASE` / `E_BUSY` |
| 3 | 施法者存在、存活、阵营正确 | `E_ACTOR` |
| 4 | 命令类型合法（该阶段允许） | `E_COMMAND_TYPE` |
| 5 | 资源足够（费用/行动点） | `E_COST` |
| 6 | 目标合法（§4.4、§9、§10） | `E_TARGET` |
| 7 | 组合整体合法（§4） | `E_COMBO` |

- 全部通过才进入结算。**任一失败：权威状态零改动，不推进正式 RNG，返回错误码 + 本地化文本键。**
- 结算在**工作快照**上进行；成功则一次性提交 `state_out / rng_out`，`BattleState.version += 1`，返回 `CommandResult{ accepted, events, state_version }`。
- 结算中若触发上限溢出（§7.4）：**拒绝整条命令**，丢弃工作快照，记录调试日志，权威状态不变。

## 4. 组合出牌规则

### 4.1 选择与顺序
- 玩家多选卡 → 选定执行顺序 → 为每张卡选定目标（`TargetSpec`）→ 一次确认。
- 【建议默认】顺序由玩家显式指定；不做自动排序。

### 4.2 费用
- 【建议默认】组合总费用 = 各卡费用之和（应用修正后），确认时**一次性扣除**。
- 费用不足 → `E_COST`，整条命令拒绝。

### 4.3 目标
- 【建议默认】每张卡各自持有目标（可不同），确认时一次性确定。
- 目标在第一张牌结算后**失效**（死亡/离场/超出重新计算的射程）时，**该卡落空**：不自动转火、不退费；该卡仍按 §4.5 移入所属区域。

### 4.4 合法性快照
- 确认时**先在工作快照上顺序预演**全部卡的合法性与结算。任何一张不合法 → `E_COMBO`，整条拒绝，零副作用。

### 4.5 牌区流转
- 接受后：全部选牌 `hand → resolving`（一次性）。
- 每张卡结算完毕：按卡定义 `resolving → discard` 或 `resolving → exhaust`。
- 结算期间抽到的牌进入 `hand`，但**不可加入本次组合**、本命令内不可选。

### 4.6 中途终局
- 组合结算中途到达 `VICTORY`/`DEFEAT`：停止后续**攻击类**效果；仍完成牌区清理（所有已承诺的卡离开 `resolving` 至 `discard`/`exhaust`），再转入终态。

### 4.7 必须明确、本文已定的规则
- 混合牌种：**允许**（除非卡定义另有约束）。
- 费用叠加：相加，一次扣除。
- 位移后射程：**按位移后的状态重新计算**。
- 击杀后后续牌：落空，不重定向、不取消、不退费。
- `OnCardPlayed`：**每张牌各触发一次**；【建议默认】组合额外触发一次 `OnComboPlayed`（供遗物/组合加成）。
- 多段攻击中击杀/反伤/死亡：**立即入触发队列**（§7），按队列顺序打断后续效果，不递归内联。

## 5. 效果与结算管线

- 效果拆为基础操作：`Damage`、`GainBlock`、`DrawCards`、`Move`、`Push`、`ApplyStatus`、`Heal`、`Summon`、`CreateCard`。新机制才加 handler；普通数值用 `.tres`。
- `EffectResolver.resolve(state_in, plan, rng_in) -> Resolution{ state_out, rng_out, events }` 为**纯函数**：不改入参、不读 UI/SceneTree、不用全局 RNG。
- `preview` = 在 clone 上调用同一 `resolve`，只读 `events`，丢弃 `state_out`。**预览与提交共享唯一代码路径。**

## 6. 伤害管线（必须按序）

```text
1. 合法性：来源存活、目标可被攻击、免疫/无敌/闪避检查
2. 攻击方修正：力量、虚弱、增伤、暴击
3. 防御方修正：易伤、减伤、护甲修正（百分比）
4. 护盾(Block)吸收：absorbed = min(block, damage)；block -= absorbed；damage -= absorbed
5. HP 变化：hp = max(0, hp - damage)
6. 生成事件与入队触发：OnDamaged(受伤方)、OnDealDamage(攻击方)、反伤(Thorns) 等
7. 死亡检查：hp == 0 → 标记死亡并入队 OnDeath
8. 队列处理 OnDeath 触发（遗物、爆炸等）
```

- **取整**：百分比修正以浮点累乘，**仅在最终 damage 上向下取整一次**，最小 0。避免逐步取整累积误差。
- **顺序**：2→3→4 的顺序是硬约束；反伤等不作为第 6 步内联执行，而是**入队**（§7），保证确定性与可中断。
- 事件携带 before/after 值，供表现层投影。

## 7. 触发系统

### 7.1 排序键（必须）
`事件阶段 → 显式 priority（小者先）→ 稳定实例 ID（小者先）`。
禁止依赖节点创建顺序、Dictionary 枚举顺序、全局 signal 递归。

### 7.2 执行模型
- 触发**入队**，在结算边界统一处理；新增触发追加到队列，**不内联递归**。
- 队内按 §7.1 排序后依次执行；执行产生的新触发再入队，重复直到排空。

### 7.3 覆盖所有战斗单位
状态（Status）与遗物（Relic）共享 TriggerSystem；状态通常随单位/战斗，遗物属于 `RunState`，进战斗后提供规则钩子。`RelicState` 保存计数器，遗物定义不保存。

### 7.4 上限（必须）
单命令触发处理上限【建议默认 1000】。超限：**拒绝该命令**、丢弃工作快照、写调试日志；**不得**留下半结算的权威状态。

## 8. 状态（Status）生命周期

- 每个 `StatusState` 记录：层数（stacks）、剩余回合（duration）、来源单位 ID。
- 每个 `StatusDef` 声明 `tick_timing`：`ROUND_START` / `OWNER_TURN_START` / `OWNER_TURN_END` / `ROUND_END`。
- 【建议默认】持续时间在**拥有者的回合结束**递减；DoT（中毒等）在拥有者回合结束时按层数结算伤害。
- 护盾（Block）：【建议默认】在拥有者**下个回合开始时清零**；不跨战斗保留。

## 9. 位移：移动 / 击退 / 交换 / 传送

- **权威占用**：`BoardState`（一格一单位，MVP）。位置查询只走 BoardState，禁止另存位置副本。
- 所有位移走**同一规则入口**，产生 `UnitMoved`、`CellExited`、`CellEntered` 事件。

| 位移 | 目的地合法性 | 落点冲突处理 |
|---|---|---|
| 移动 Move | 路径全可走、占用为空、在行动预算内 | 不可达 → 命令拒绝 |
| 击退 Push N | 逐步推进，每步须在盘内且未被阻挡单位占据 | 遇**墙/单位**即**停在其前**；【建议默认】不造成碰撞伤害（可作为后续变体） |
| 交换 Swap | 两格各有可交换单位 | 直接交换位置，不要求路径/射程 |
| 传送 Teleport | 目的地在盘内、占用为空（或按效果定义的占用规则） | 忽略路径与视线 |

- 被推出盘外：**不**移出，改为停在边缘（或按效果自定义）。此条与"墙阻挡"分开，必须明确。
- 位移后可移动性/射程**按下一次查询重新计算**，不缓存。

## 10. 视线与射程

- **LoS 算法**【建议默认】：格子中心连线用 **supercover**；`blocks_los` 地形阻挡；**起点与终点格本身不阻挡**；连线恰穿过两个阻挡格之间的**角**时判为**阻挡**（无穿角窥视）。
- LoS **对称**：`has_line_of_sight(a, b) == has_line_of_sight(b, a)`。
- 区分三件事，不得混用：**移动可达性**（可走路径）/ **技能射程**（含 LoS 与否）/ **效果覆盖**（AOE 形状）。
- 陷阱可允许进入但产生效果；远程技能不要求存在可步行路径。

## 11. 胜负判定

在每个**结算边界**评估：

- `VICTORY`：所有敌方单位死亡且玩家存活。
- `DEFEAT`：玩家单位死亡。
- **同时死亡**（同一结算批次内玩家与最后敌人同时归零）【建议默认】：**判 `DEFEAT`**（玩家死亡优先）。若要改为 `VICTORY`，仅需改此条并加测试。
- 到达终态后：停止新攻击效果，完成 §4.6 牌区清理，产生 `BattleResult`（胜负、持久 HP、明确允许持久化的变化、battle ID）交 `RunSession` 消费。**临时护盾、战斗增益、抽牌顺序不写回单局。**

## 12. 随机与确定性

### 12.1 随机流
路线 / 遭遇 / 战斗 / 奖励 各一条流，视觉随机另建。子流派生用随 `game_version` 固定的函数（【建议默认 `splitmix64(run_seed, stream_id)`】），**禁止** `seed(run_seed + i)` 之类脆弱写法。

### 12.2 推进规则（必须）
- 只有**被接受的命令**推进**正式**随机流。
- 预览在**克隆的 RNG** 上运行，**绝不**推进正式流。
- 结算内一切随机必须取自传入的 `rng` 参数，禁止全局随机。

### 12.3 命令去重
每个命令带唯一 `command ID`；`BattleState` 保存**有界**已见命令 ID 集合（【建议默认：最近 64 条，FIFO 淘汰】）。重复命令幂等：返回首次结果，不二次结算。命令 ID 方案与去重表随存档持久化。

### 12.4 持久化计数器（必须）
`next_uid`、`next_event_seq` 为 `BattleState` 字段并随存档保存——否则读档后 UID/触发顺序改变，破坏确定性与回放。

### 12.5 可回放范围
相同 `game_version` + `content_version` + `rule_version` + `seed` + 命令日志 → 相同结果。存档记录 `game_version` / `content_version` / `schema_version`；**旧 build 读到更高 schema 版本必须拒绝**，不尝试解析。

## 13. 待决问题（Open Questions）

1. 移动是否消耗独立行动点，或仅由卡牌触发？（架构文档 §5.1 保留入口，规则未定）
2. 玩家 `PLAYER_END` 是否弃手牌，还是保留？
3. 护盾清零时机：回合开始 vs 回合结束（本文默认回合开始）。
4. 击退遇到单位：停住 / 连锁推动 / 双向碰撞伤害——原型需手感确认。
5. 是否存在借机攻击（AoO）？MVP 默认无。
6. 组合是否允许"抽牌后又用新牌"的连锁？本文默认不允许（确认时冻结选择）。
